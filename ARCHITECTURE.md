# Architecture

How little-doc-editor is built. For what it does and how to deploy it, see [README.md](./README.md); for local setup, [DEVELOPER.md](./DEVELOPER.md). The reasoning behind each choice lives in the numbered Decisions Log in [SPEC.md](./SPEC.md), referenced below as "Decision N" rather than restated.

## The three services

| Service    | Path        | Stack                                         | Responsibility |
| ---------- | ----------- | --------------------------------------------- | -------------- |
| `api`      | `api/`      | Go, chi, pgx + sqlc, golang-migrate, go-oidc  | REST API: auth, spaces/pages/attachments/sharing/invites/history/export/search, admin settings, in-process history cleanup, metrics |
| `frontend` | `frontend/` | Vue 3, Vuetify, Vite, Pinia, Tiptap           | Static SPA served by nginx; talks to `api` over REST and to `collab` over WebSocket |
| `collab`   | `collab/`   | Node, TypeScript, Hocuspocus (Yjs)            | Live editing: holds the Yjs document per open page, authorises each connection, persists snapshots and writes the result back to `pages.content` |

They are separate Deployments so they scale and upgrade independently (Decision 12). `api` is stateless. `collab` keeps live document state per replica but any replica can serve any page, because updates fan out through Redis (Decisions 3, 20). `frontend` is a pure static asset server.

External dependencies are always bring-your-own, never bundled (Decisions 5, 18, 29): PostgreSQL (all durable state, including search), Redis (collab fan-out, shared rate-limit counters, collab notifications) and S3-compatible object storage (attachment bytes).

The SPA is served from its own origin. `api` and `collab` are reached at their own hosts (or same-origin `/api/v1` and `/collab` paths when a proxy routes them there); the frontend learns the URLs at container start from `/config.js`, generated by `frontend/docker/40-lde-config.sh`, which also builds the Content-Security-Policy. Browsers talk to `api` and `collab` directly; the two services never call each other over HTTP. `api` signals `collab` only through a Redis channel (below).

## Authentication and authorization

**One session token, two verifiers.** `api` issues an HS256 JWT (`api/internal/sessiontoken`) on password login, OIDC login, invite redemption and share-link redemption. The claim shape is `sub` (user id) or `guestIdentityId`, `displayName`, and, for share-link guests only, `shareLinkId`. `collab` verifies the same token with the same `SESSION_JWT_SECRET` (`collab/src/auth.ts`); the chart exposes that as the single shared `sessionJWT` value. Both sides decode strictly, so a re-spelled token cannot dodge the revocation lookup (Decision 37). A JWKS-based alternative to the shared secret is not built.

**Tokens carry identity, not permission.** Authorization is re-read from Postgres on every request (`api/internal/authz`) and on every collab connection and message (`collab/src/access.ts`, re-checked at most every `ACCESS_RECHECK_MS`, plus a background sweep). So demoting a member, disabling a user, revoking a share link or logging out takes effect immediately, including on already-open WebSockets, instead of at token expiry.

- **Space roles** (Decisions 7, 24): owner > admin > editor > viewer, per space, no per-page ACLs. A user's effective role is the highest of their direct role, the roles of their IdP groups (Decision 40) and the instance-wide `defaultMemberRole`. Org admins pass every check. `api` and `collab` implement the same rule against the same tables; a change to one must be mirrored in the other.
- **Share-link guests** (Decisions 6, 21): redeeming a link (`POST /share/{token}/redeem`, display name mandatory, optional password) yields a guest token bound to `shareLinkId`. The link's page scope (the page plus descendants), permission (view or edit), expiry and revocation are looked up from `share_links` on each request and collab connection, not copied into the token. View-permission and locked pages give a read-only collab connection. Guests never get history, the share dialog, or space chrome.
- **Revocation** (Decision 37): `POST /auth/logout` records the SHA-256 of the token in `sessions.revoked_at`; both services refuse it from then on.
- **Sign-in methods** (Decisions 11, 14, 38, 39): internal argon2id accounts created only by admin invite or the bootstrap admin, and a single OIDC issuer with authorization-code + PKCE and just-in-time provisioning (an IdP identity is never linked to an existing account by email). Internal login can be disabled instance-wide, with an environment-variable break-glass for the bootstrap admin.
- **Abuse limits** (Decisions 35, 36): fixed-window rate limits on login, share and invite redemption and SSO endpoints, counted in Redis (falling back to per-replica memory), keyed by a client IP that honours `X-Forwarded-For` only from `TRUSTED_PROXIES`.

## Content and the collaboration data flow

The source of truth for a page is **ProseMirror/Tiptap JSON** in `pages.content` (Decision 4); Markdown and HTML are generated on demand. The editor schema is the StarterKit plus an `attachmentImage` node (stores only an attachment id, never a URL) and Mermaid as a `codeBlock` with `language: 'mermaid'`. It is defined twice and must be kept identical: `frontend/src/editor/extensions.ts` and `collab/src/schema.ts`. `api` itself knows nothing about CRDTs (Decision 1); `collab` owns the Yjs conversion (`collab/src/convert.ts`).

1. **Connect.** The editor opens a Hocuspocus WebSocket to `collab` with the session token and the page id as the document name. `collab` authenticates the token, then authorises that identity for that page, then joins (or creates) the room.
2. **Load.** The first load of a page with no `collab_documents` row converts `pages.content` into a Yjs document and writes a seed row. The seed uses a fixed Yjs client id, so two replicas seeding at once produce identical updates that merge without duplicating content.
3. **Edit and fan-out.** Clients exchange Yjs updates through the room. With several `collab` replicas, updates and presence (awareness) are relayed through Redis. Awareness is rewritten server-side: the display name is pinned to the token's, and read-only connections get no cursor.
4. **Store (merge-on-write).** Debounced by Hocuspocus and retried with backoff, each store merges the Yjs snapshot into `collab_documents` and, in the same transaction, updates `pages.content`, `pages.search_vector` and `pages.updated_at`, and records a revision (same debounce rules as `api`). That is how `pages.content`, search, export and history stay in sync with live edits, and why `api` can read consistent content without touching the CRDT.
5. **Edits that bypass the editor.** `PUT /pages/{id}/content` (and a revision restore) writes `pages.content` directly. After committing, `api` publishes the page id on the Redis channel `lde:page-content-replaced`. Every `collab` replica holding that room merges the new content into the live document as real Yjs delete/insert operations (never a re-seed, which would corrupt peers' ids), so open editors update at once. Delivery is best-effort; if a message is lost, `collab` detects the difference at its next store. The last write wins.

If `collab` is unreachable the SPA shows the last saved content read-only, so unsynced edits are never silent.

## Storage

**PostgreSQL** holds everything durable. Migrations are golang-migrate files in `api/db/migrations/`, applied by `api/cmd/migrate` (a Helm pre-install/pre-upgrade hook Job in the chart), and queries are generated by sqlc into `api/internal/db/`. The main tables:

| Area | Tables |
| ---- | ------ |
| Identity | `users`, `groups`, `group_members`, `sessions` (incl. revocation), `guest_identities`, `invites` |
| Structure and access | `spaces`, `space_members` (user or group principals), `pages` (tree via `parent_id` and fractional `position`) |
| Content | `pages.content` (ProseMirror JSON), `pages.search_vector`, `page_revisions`, `attachments`, `collab_documents` (Yjs snapshots) |
| Sharing | `share_links`, `share_link_access_logs` |
| Operations | `instance_settings` (admin attachment policy, login toggle), `history_cleanup_logs` |

**S3-compatible object storage** holds attachment bytes only; `attachments` rows hold the metadata. The api uploads in one request, sniffs the real content type (not the client's header or filename) and enforces the admin allowlist and size cap (Decision 17, 45). Downloads go through `GET /attachments/{id}` with the bearer token, and the frontend shows them from a tab-local `blob:` URL; there are no presigned or signed URLs, so permissions are checked on every view and revocation is immediate (Decision 34). A filesystem (PVC) backend exists for small single-replica installs.

**Revisions and cleanup** (Decisions 9, 42, 43): a revision is written on content saves unless history is off for the page, nothing changed, or the same author saved within the debounce window. An in-process job inside `api` (schedule `HISTORY_CLEANUP_SCHEDULE`, one replica per tick via a Postgres advisory lock) prunes by each space's maximum count and age.

## Search

Postgres full-text search behind a `SearchIndexer`/`SearchQuerier` interface (`api/internal/searchindex`, `searchapi`; Decision 2). Plain text is extracted from the ProseMirror JSON and stored in `pages.search_vector` (GIN index) on every create and save, by `api` on direct writes and by `collab` on live-edit stores, using the same extraction. Queries run per space through `GET /spaces/{id}/search`, which requires at least the viewer role in that space. The interface exists so Meilisearch or Typesense could replace it later. The SPA does not expose search yet (tracked in [NEXT.md](./NEXT.md)).

## Export

`api/internal/export` renders Markdown and HTML server-side from the stored JSON (everything escaped, unsafe link schemes dropped; Decision 44). PDF is not generated server-side: the api returns a print-optimised HTML document and the browser prints it from a hidden sandboxed iframe.

## Observability

Prometheus `/metrics` is served on a dedicated listener per service (`api`: `METRICS_ADDR`; `collab`: `METRICS_PORT`), never through the ingress, and labels use route patterns, never raw paths, because share and invite tokens are path segments (Decisions 27, 47). The chart can create a `ServiceMonitor`. `api` exports OTLP traces when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; `collab` has metrics only.

## Frontend structure

`src/pages/` (routes), `src/components/` (page tree, editor shell, dialogs, drawers), `src/editor/` (Tiptap extensions, collab session, node views), `src/stores/` (Pinia), `src/api/` (client generated from `api/openapi.yaml` with `npm run generate:api`), and `sw/` (the service worker for installability and the Android share target; Decisions 31-33). UI gating uses the `my_role` and `can_edit` fields the api reports; the api enforces regardless.
